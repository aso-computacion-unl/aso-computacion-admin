# ASO Computación — Admin

Content admin for the ASO Computación student association. It manages the content (events and photos, news, FAQ, free terminal commands, board, pillars, socials, sponsors, site texts) that the static landing consumes at build time, and it also hosts the student forum and the event registration pages.

**Deploying:** see [DEPLOY.md](DEPLOY.md) (Vercel, Neon, Cloudinary, environment variables, seeding, first-deploy checklist).

**The whole system** (this admin plus the landing): see [ARQUITECTURA.md](ARQUITECTURA.md).

## Stack

- Next.js 16 (App Router) + React 19, TypeScript
- Hexagonal layers: `src/domain`, `src/application`, `src/infrastructure`, `src/interface` (boundaries enforced by `architecture-boundaries.test.ts`)
- Prisma 7 + PostgreSQL (`pg` driver through `@prisma/adapter-pg`; the client is generated into `src/generated/prisma`)
- Cloudinary for images (SDK confined to `src/infrastructure/storage`)
- Vitest 5 for unit and Prisma integration tests; Playwright (Chromium) for end-to-end
- Sentry for optional error tracking, Cloudflare Turnstile for the open registration form, `arctic`/`jose` for Google sign-in and signed tokens
- Deployed on Vercel (the landing it feeds is on Cloudflare Pages)

## Image uploads

Uploads accept JPEG, PNG and WebP up to 5 MB. The minimum width is chosen by each caller (event photos 1200 px; board photos a smaller value). Cloudinary reports the real width after upload; an image narrower than the caller's minimum is destroyed immediately and rejected with `IMAGE_TOO_SMALL`. Images are otherwise retained: replacing a photo never deletes the previous asset, and moving an item to the trash keeps its images too: stored files are destroyed only when an item is deleted for good from the trash (see [Trash](#trash-soft-delete)).

## Admin UI behavior

- **Route states.** `app/admin/error.tsx` (Spanish message, "Reintentar" calls `reset()`, only the error digest is logged and shown, never the message or stack) and `app/admin/not-found.tsx`. An unknown `/admin/<x>` is caught by `app/admin/[...rest]/page.tsx`, which only calls `notFound()`: Next then renders `app/admin/not-found.tsx` inside the admin layout (top bar, navigation) with status `404`, instead of the root fallback. The catch-all adds no access: the proxy and the layout's `requirePageSession()` run first, so without a session `/admin/<x>` redirects to `/login` like any admin address, and any specific route (`/admin/events`, `/admin/events/<id>/edit`, the CSV export) wins over it. `app/not-found.tsx` covers URLs outside `/admin` and `/foro` (and `/api/*`, which the catch-all does not touch). `e2e/not-found.spec.ts` and `unknown-segment-routes.test.ts` cover it. There is deliberately no `loading.tsx` (nor any `<Suspense>`) under `app/admin`: with Next 15.5 / React 19.2 a revealed Suspense boundary there drops the refresh after a server action with `revalidatePath`, leaving lists stale (the row stays after trash/publish) until an unrelated re-render. `src/tests/unit/app/admin-route-boundaries.test.ts` enforces it. Not re-tested since the upgrade to Next 16 / React 19.3: try a boundary there before dropping the guard.
- **Navigation.** Four areas plus the home, all in `app/admin/_components/nav-items.ts` (`AREA_NAV`): the logo is **Inicio**, and the rail (desktop) or the bottom tab bar (phone) holds **Landing**, **Inscripciones**, **Foro** and **Ajustes**. Each area keeps lit every page it owns (`matches`, longest pattern wins, so the registrations of one event light Inscripciones and not Landing); URLs did not change. Landing and Ajustes put a tab strip (`AreaTabs`, `app/admin/_components/area-tabs.tsx`) at the top of their pages: **Contenido** has Línea de tiempo (`/admin/events`), Novedades, Preguntas, Directiva and a «Más ▾» menu with Pilares, Comandos, Aliados and Redes, plus one «+ Crear» for the current type; **Ajustes** has Equipo, Mis sesiones, Textos del sitio, Historial and Papelera (`/admin/usuarios`, `/admin/sesiones`, `/admin/settings`, `/admin/registro`, `/admin/papelera`). The admin-only Ajustes tabs show a lock and are hidden from editors (`adminOnly`); the pages and actions still enforce the role, and `/admin/ajustes` opens the first tab the role can use. The active tab carries `aria-current="page"`; on a phone the strip scrolls sideways inside its own box. `area-tabs.test.ts` and `nav-items.test.ts` cover it.
- **Thumbnails.** Admin lists and previews never load the Cloudinary original for a small image. `thumbnailUrl(url, width, height?)` (`lib/cloudinary-thumbnail.ts`) inserts `w_<2×width>[,h_<2×height>],c_fill|c_limit,f_auto,q_auto` into an image delivery URL (`c_fill` with a height, `c_limit` without). It goes after any transformation already in the URL and before the version segment; without a version segment it goes right after `/upload/`. Non-Cloudinary URLs (and invalid widths) come back unchanged. Images stay plain `<img>` with `loading="lazy"`, `decoding="async"` and explicit `width`/`height`.
- **Toasts.** `ToastProvider` (`app/admin/_components/toast.tsx`) wraps the admin content; `useToast().notify(message)` shows a short success message in an `aria-live="polite"` region, auto-dismissed after 5 s (`notify(message, action?)` can add one button, used by the «Deshacer» of a removal) (paused while hovered or focused, closable, at most 3 at once: `src/interface/admin/toasts.ts`). `useRunAction().run(action, onSuccess, successMessage)` raises it after a successful action: publish/unpublish, move to the trash, reorder (the toast is the screen-reader announcement of the new position) and a photo's description. Uploading photos reports how many went through. Saving a form (`FormFeedback` in `app/admin/_components/form-parts.tsx`) also toasts "Cambios guardados." and keeps the same line next to the button; the toast is the screen-reader announcement, so that line is not a live region. `FormFeedback toast={false}` skips it where the form confirms on its own (creating a forum category toasts «Categoría creada.»). Every error stays inline where it happened.
- **Form validation.** Every admin form shows all its invalid fields at once. `useControlledForm` (`app/admin/_components/use-controlled-form.ts`) first checks the browser's own constraints (`required`, `type="url"`/`"email"`; a field of only spaces counts as empty) and, if some fail, does not call the action. Otherwise the server answers: `mapActionError` (`src/interface/admin/action-result.ts`) returns one `fieldErrors` entry per rejected field of the Zod schema, but the domain constructors behind it throw on the first broken rule (slug format, publication window order, link label without link), so those still surface one per round trip. Both sides use the same Spanish texts, kept in `src/interface/admin/field-messages.ts` (shared `FIELD_MESSAGES` plus the per-entity overrides the actions and the forms both pass in). A failed submit shows «Revise N campos.» (`Revise 1 campo.` in the singular; `FormFailure` in `form-parts.tsx`, inside `FormFeedback`) and moves the focus to the first `aria-invalid` field. That summary is the one `role="alert"` of the failure: a field's own error is not an alert, it is read with its field through `aria-describedby`. A successful save keeps both the toast and the inline «Cambios guardados.».
- **Unsaved changes.** `useControlledForm` compares the values with what the server last stored (the initial values, then each accepted save). While they differ it asks the browser to confirm closing or reloading the tab (`beforeunload`) and marks the page as having unsaved changes; the back link of `PageHeader` (`GuardedBackLink` in `form-parts.tsx`) then opens an in-page question, «Tiene cambios sin guardar», with «Seguir editando» focused and «Salir sin guardar». A failed save keeps the guard; a successful one, or typing the original text back, clears it. Only the back link asks: another in-app link (rail, tabs) leaves without asking. The site settings form uses the same guard.
- **Autosave of drafts.** An edit page of an unpublished draft saves by itself, in every editor with a draft state (events, FAQs, news, board, pillars, commands, sponsors, socials; not the site texts, which have none). It is the `autosave` option of `useControlledForm`, which the edit pages turn on through the form's `autosave` prop; create pages never pass it, because a save there would create a row. It runs only while the stored item and the form are both drafts (`isPublished` false): a published item, or a draft whose switch was just turned on, goes through «Publicar» and «Sí, publicar». It waits `AUTOSAVE_DELAY_MS` (1.8 s) after the last keystroke, checks the browser constraints first and skips a form that is not valid (nothing is shown), then calls the same update action as the button. One request at a time: typing while it is out is saved after it answers, and an answer never touches the text in the fields. The status next to the button (`FormFeedback`, `data-slot="autosave-status"`, a polite live region) says «Guardando…», then «Guardado»; a failure says it in a few words (the error of the action, else «No se pudo guardar. Use el botón.») and is not retried until the next edit; the button keeps working. There is no toast, and an accepted autosave clears the unsaved-changes guard. The update action is the one the button uses, so each autosave also writes its audit entry (Historial records the edit), but it does not ask for a site rebuild: a draft that stays a draft is not on the landing (see «Landing rebuilds»).
- **Optimistic publish toggle.** `PublishedToggle` flips at once (`useOptimistic`) while the server action runs. If the action fails the switch goes back to the confirmed state and the inline error explains why. The switch keeps `role="switch"` and `aria-checked` equal to what is shown, with `aria-busy` while pending.
- **Status filter.** The events and news lists have a Todos / Publicados / Borradores filter, each option with its count, driven by `?estado=publicados|borradores` (anything else, or a repeated param, is Todos: `parseStatusFilter`). The filtering is server-side: the page maps the param to a `ListCriteria` (`{ status: "published" | "draft" }`, `statusCriteria`) that `ListEventsUseCase` / `ListNewsItemsUseCase` hand to `EventRepository.list(criteria)` / `NewsRepository.list(criteria)` (a `where isPublished` in Prisma), and the counts come from `countByStatus()` (one `groupBy`), so they do not change with the filter. The lists are paged (see **Search and pages** below), so no row is ever hidden by a limit. The ordered lists (FAQ, commands, pillars, socials, board, sponsors) have no status filter on purpose: their rows move one place at a time inside the whole list, and a filtered view would show positions and move buttons that no longer match it.
- **Search and pages.** Events, news, FAQ and commands lists take `?q=` (trimmed, whitespace collapsed, control characters dropped, at most 80 characters; a repeated param means no search) and `?pagina=` (a plain positive integer, else page 1; a page past the last shows the last). `PAGE_SIZE` is 20 rows (`src/interface/admin/list-params.ts`). The search and the status filter are applied by the repository (`ListCriteria`), the page by its `offset`/`limit`, and the total comes back with the page so the pager and counts are exact. `listHref` leaves defaults out, so every view has one shareable URL. While a list is searched the ordered lists show no place number (`··`) and no move buttons, because a place in the whole list is unknown for a subset.
- **Bulk actions.** On every content list, each row has a checkbox, and as soon as one is ticked a bar appears (only then; it sticks to the bottom of the screen, after the rows, so the rows never jump) and offers «Seleccionar todo en esta página», «Publicar», «Pasar a borrador» and «Mover a la papelera». Each asks for a confirmation that says how many items and what happens. The two server actions `bulkSetPublished(kind, ids, published)` and `bulkTrash(kind, ids)` (`src/interface/admin/bulk/actions.ts`) accept up to 50 ids (`BULK_MAX_ITEMS`) of one of the eight content kinds (events, news, FAQ, commands, socials, pillars, board, sponsors), start with the same session guard as every single-item action and repeat the single-item use cases one after the other, so each rule (publication window, slug, trash cascade) still applies per item and each item that changes writes its own audit entry. A refused item does not stop the rest: the result lists every id with its Spanish reason, successful ones leave the selection, failed ones stay selected with the reason so they can be retried. One landing rebuild is requested for the whole batch, and only if the public site could have changed. The selection only holds ids of the current page.
- **Drag-and-drop reorder.** The six ordered lists (FAQ, commands, social links, pillars, board, sponsors; `REORDER_KINDS`) can be reordered by dragging the grip at the left of a row (`@dnd-kit`: mouse, touch and keyboard — focus the grip, Space to pick up, arrows to move, Space to drop, Escape to cancel — with Spanish screen-reader announcements). A drop calls `reorderContent(kind, id, position)` (`src/interface/admin/reorder/actions.ts`), where `position` is the 0-based place in the **whole** list (page offset included); `ReorderOrderedContentUseCase` clamps it, moves the item and renumbers the list 0..n-1. It has the same role (EDITOR), audit entry (`<kind>.move`) and rebuild request as the one-step move buttons, which stay as the other way to move a row. The new order shows at once (`useOptimistic`) and goes back with an inline message if the server refuses. A drag stays inside its page; to move a row to another page use the move buttons. Dragging is off while a list is searched, like the positions and the move buttons. Events and news are ordered by date and have no handle.

## Events

`/admin/events` manages events and their photo gallery (list, create, edit, publish toggle, move to the trash).

- An event has a slug (derived from the title, editable), an optional date (future = upcoming on the landing, past = history), an optional type (`taller`, `charla`, `evento`, `comunidad`), optional `hora` / `lugar` / `para`, an https-only link, up to 8 highlights and a `featured` flag. New events are drafts.
- **List layout.** The status tabs and the search share one row, the first row follows right after, and the legend («Cómo leer la línea») sits below the list and its pager. The bulk-action bar only appears once a row is ticked (see **Bulk actions**).
- **Creating continues on the photos.** `createEvent` redirects to `/admin/events/<id>/edit?creado=1#fotos` (`createdEventPath`, `src/interface/admin/events/created-flag.ts`), because photos need an existing event. The edit page reads the one-time `creado=1` flag on the server (exactly `1`; anything else is a plain visit) and renders `EventCreatedArrival`, which shows the toast «Evento creado. Agregue las fotos.», puts focus on the photo drop zone (the browser scrolls it into view) and replaces the URL with `/admin/events/<id>/edit#fotos` (`router.replace`, no scroll), so a reload or a shared link shows no toast again. On a phone the «Datos / Fotos (N)» chips mark the section in view with `aria-current="location"`. Tests: `actions.test.ts` (redirect target), `event-created-arrival.test.ts` (toast, focus, flag removed) and `admin.spec.ts` (end to end).
- **Month-only dates.** When the day is not confirmed yet, pick "Solo mes" in the form (a month picker instead of the date picker). The event keeps `datePrecision: "month"` and its date is stored as the **first of that month**; with no date the precision is always `day`. The timeline shows it as `feb 2026` and orders it as the 1st of that month, so the current month already counts as past (the landing uses the same rule, with "today" in America/Guayaquil). The column is an add-only migration (`datePrecision` text, default `day`, `CHECK` for `day`/`month`), so existing events stay exact dates.
- Photos need alt text (1–200 characters), are at least 1200 px wide, and an event keeps at most 12 active photos. "Quitar" on a photo of the gallery deactivates it; the Cloudinary asset is kept. Moving an event to the trash keeps its photo rows (active or not) attached, and they come back with it on restore. Only deleting it for good from the trash removes the photo rows and then destroys their stored files, active or not; when a destroy fails the delete still succeeds and the leftover `publicId`s are logged.
- **Registration.** The form's "Inscripción" section chooses, per event, how people sign up: none, with a UNL Google account, or with an open form, plus optional seats and a deadline (Ecuador time). See "Event registration".
- If the database write fails after an upload, the uploaded asset is destroyed (best effort, logged when that fails) and the original error is reported.

## News

`/admin/news` ("Novedades") manages the landing's news: a list (newest publication date first, drafts included), create, edit, publish toggle and move to the trash.

- A news item has a slug (derived from the title, editable, same rules as events; it is the landing's `/novedades/<slug>` URL and a repeated title gets `-2`, `-3`, ...), a title (1–120 characters), a summary (1–280), a body (1–10000), a publication date and an optional cover. New items are drafts.
- **Body.** A Markdown subset (paragraphs, `**bold**`, `*italic*`, `[links](https://...)` and `- lists`), stored exactly as written; the admin never converts it. The landing renders it without raw HTML and only follows `https:` links. A line break in the form is stored as `\n`.
- **Publication date.** A calendar day (`YYYY-MM-DD`), today in Ecuador (UTC-5) when left blank on create and unchanged when left blank on edit. Items are ordered by it, newest first, then by creation time.
- **Cover.** Uploaded through the shared upload flow (folder `news`, JPEG/PNG/WebP up to 5 MB, at least 1200 px wide) and needs alt text (1–200 characters). ## Media library

There is no Medios screen: the library listing was removed from the admin. The only image tool left is the unused-image cleanup, in Ajustes → Papelera (below). `/admin/medios` and `/admin/medios/limpieza` redirect to `/admin/papelera` and `/admin/papelera/imagenes` so old bookmarks keep working. The use cases that list the library with where each image is used (`ListMediaLibraryUseCase`) are kept in the application layer, but no page calls them.

- **How the storage is read.** `MediaLibraryPort` (`CloudinaryMediaLibrary`, the Admin API `resources` call with the folder as `prefix`) returns one page of images and an opaque cursor; `MediaUsageReader` (`MediaUsagePrismaReader`, one query per owning table with `publicId IN (...)`) says what uses them. Pages are cursor based (`?despues=<cursor>`, validated before it reaches the provider): there is a «Revisar la página siguiente» link and «Volver al principio», no page numbers, because the provider does not offer them.
- **Unused-image cleanup** (`/admin/papelera/imagenes`, ADMIN only, linked from Papelera as «Limpiar imágenes sin uso»). Replacing or removing an image never deletes its file (see Image uploads), so unused files pile up in the storage; this is how they are removed, in two separate steps. **1. Dry run:** the page scans one storage page at a time (100 images, one provider call, «Revisar la página siguiente» for the next) and lists the images no row points at, **only in the folders whose owners the usage reader counts** (the allowlist, below). It deletes nothing and its use case (`FindOrphanImagesUseCase`) is not given the destroy call. **2. Explicit deletion:** the admin ticks images and confirms («Sí, eliminar definitivamente»; irreversible, stated in the prompt); only then `deleteOrphanImages(publicIds)` runs (max 5 ids per request, ADMIN guard first, ids must look like our own public ids, no `.` or `..` segments). The choice is not trusted: `DeleteOrphanImagesUseCase` looks each image up again and skips it unless it still exists **under the app's folder**, is **at least 24 hours old** (an upload is stored before the row that owns it is saved, so a young unused image may be mid-save; those are listed but cannot be ticked) and **still has no use** (event photos, including removed ones, pillar images, news covers, board photos and sponsor logos, trashed rows included). A failure on one image never stops the others. Each destroyed file writes a `media.delete_orphan` audit entry (entity «Imagen») **right after that file is destroyed**, not after the batch, so a request the platform cuts short never leaves a deleted file unaudited. **Why 5 per request:** admin functions run at most 30 s (`maxDuration`, `app/admin/layout.tsx`); 10 s are kept for cold start, session, queries and revalidation, and each image is two provider calls one after the other (the lookup, then the destroy), up to 2 s each in a slow spell, so 4 s per image: (30 − 10) / 4 = 5 (`ORPHAN_DELETE_MAX`, derived in `media-orphans.use-cases.ts`). The screen cuts a longer selection (up to the whole page) into requests of 5, sent one after the other; what finished is kept and shown, a refused or unanswered request stops the rest (the message says some images may already be gone). The result of every image is shown, with the reason when it was kept, and a deleted file is never shown as an error. A provider answer other than `{ result: "ok" }` to the destroy counts as a failed deletion: nothing is reported or audited as deleted. There is no scheduled or automatic deletion.
- **Cleanup fails closed: the folder allowlist.** An image is only ever offered or destroyed when its folder is one whose owner the usage reader counts. The list is one constant, `MEDIA_OWNERS` in `src/application/media-owners.ts` (model, column and upload folder for each owner: `EventPhoto.publicId` → `events`, `Pillar.imagePublicId` → `pillars`, `NewsItem.coverPublicId` → `news`, `BoardMember.photoPublicId` → `board`, `Testimonial.photoPublicId` → `testimonials`, `Sponsor.logoPublicId` → `sponsors`); `MANAGED_MEDIA_FOLDERS` is derived from it and the folder names come from the same constants the upload use cases use. An image in any other folder (say `gallery/`), nested deeper or at the root of the app's folder is not scanned for use, not offered, and refused by the deletion with «Está en una carpeta que esta revisión no cubre» even if its id is posted directly; the dry run page says how many images it left out. **Adding a new image column** (any `*PublicId` in `prisma/schema.prisma`): add its row to `MEDIA_OWNERS` and its query to `MediaUsagePrismaReader` in the same change. The unit test `media-owner-coverage` parses the schema and fails with «… stores a Cloudinary public id but is not listed as a media owner …» until both are done, so cleanup can never delete images of a feature the reader does not know.
- **Nothing is written by the library.** The library adapter has no upload or destroy call. Without Cloudinary credentials, or when the provider does not answer, the page says so instead of failing (the error is logged and reported). The Admin API has an hourly rate limit on the free plan: each page is one call.

## Trash (soft delete)

Every content type (events, news, FAQ, free commands, social links, pillars, board, sponsors) is deleted in two steps. The destructive action on a row is now **«Mover a la papelera»**; the row is only removed, with its stored images, by **«Eliminar definitivamente»** on `/admin/papelera`. Event photos (`EventPhoto`) keep their own `isActive` flag and have no trash of their own.

- **Data model.** Seven tables (`Event`, `Faq`, `TerminalCommand`, `SocialLink`, `Pillar`, `NewsItem`, `BoardMember`) got a nullable `deletedAt` (`NULL` = live), and the S9 tables (`ImpactStat`, `Testimonial`, `Sponsor`) are created with it (the first two are no longer managed; rows already in their trash are kept but cannot be listed or purged any more). Trashing sets it **and unpublishes the row**, so a restore can never put something back on the public site by surprise. A trashed event cascades nothing: its photos stay attached and return with it.
- **Uniqueness applies to live rows only.** `Event.slug`, `NewsItem.slug`, `Faq.command` and `TerminalCommand.command` are enforced by partial unique indexes (`... WHERE "deletedAt" IS NULL`, named `*_live_key`), written in raw SQL in the `add_soft_delete` migration because Prisma cannot express them (`schema.prisma` carries a comment on each column and `prisma migrate diff` reports no drift). Two trashed rows may share a slug, and a trashed row never blocks a new one. The Cloudinary `publicId` columns keep their plain unique indexes: a trashed row still owns its asset.
- **Every read ignores trashed rows.** The repositories filter `deletedAt IS NULL` in `getById`, `list`, `countByStatus` (the status filter counts), `slugExists`, `update`, `saveOrder` (reordering renumbers live rows only), the command-name registry (`findOwner`) and the photo upload lock, and `GET /api/public/content` is built from those same `list()` calls, so a trashed item never reaches the landing. The trash operations (`trash`, `getTrashed`, `listTrashed`, `restore`, `purge`) are the only methods that see trashed rows; they are written once in `TrashablePrismaRepository`.
- **Restore** (`RestoreContentUseCase` and its per-type subclasses) brings the item back **as a draft**; ordered lists (FAQ, commands, socials, pillars, board) append it at the end (`max(sortOrder) + 1`), so positions never collide. If a live item has taken its slug or command in the meantime, the restore is refused with a Spanish message («No se puede restaurar: … Cambie o elimine ese … y vuelva a intentarlo.») and nothing changes; the partial unique index backs this check against races.
- **Delete for good** (`PurgeContentUseCase`, `PurgeEventUseCase`) only accepts an item that is already in the trash; a live one is refused. The row is removed first and its Cloudinary assets are destroyed afterwards, best effort (a failed destroy is logged with its `publicId`, never an error).
- **No automatic expiry.** Nothing leaves the trash unless an admin deletes it for good.
- **Deploy hook.** Saving a draft that stays a draft asks for no rebuild (see «Landing rebuilds»). Trashing a *published* item asks the landing to rebuild (the public content changed); trashing a draft, restoring (always a draft) and deleting for good do not.
- **UI.** The delete button of each row reads «Mover a la papelera»; its toast («Movido a la papelera») has a **Deshacer** button that restores the item. `/admin/papelera` (the «Papelera» tab of Ajustes) lists the trash by type, newest deletion first, with «Restaurar» and «Eliminar definitivamente» (the latter asks for confirmation and says it cannot be undone and which files go with it). The two server actions, `restoreTrashed(kind, id)` and `purgeTrashed(kind, id)`, are guarded like every other action (`restoreTrashed` by `requireSession`, `purgeTrashed` by `requireRole("ADMIN")`) and refuse an unknown `kind`.
- **Not covered.** Event photos are not trashed (they use `isActive`), and the seed's rollback of a half-created pillar or member trashes and then deletes it for good, so a failed seed leaves nothing behind.

## Public read API

`GET /api/public/content` is what the landing fetches at build time: one JSON snapshot of the **published, non-trashed** content in display order (events and news also only inside their publish window, see "Scheduling and preview"). It needs no session (it is outside the proxy matcher on purpose, so the proxy never runs for it; `route-protection.test.ts` fails if any other route is reachable without a session) and it only reads.

```jsonc
{
  "version": 1,                       // older name of schemaVersion, same value
  "schemaVersion": 1,                 // version of this contract, see below
  "generatedAt": "2026-10-22T16:00:00.000Z",
  "events":   [{ "slug", "title", "description", "date", "datePrecision", "type", "commitMessage", "hora", "lugar", "para", "featured", "linkUrl", "linkLabel", "highlights", "photos": [{ "url", "width", "height", "alt" }], "registration": {…} | null, "calendarUrl": string | null, "structuredData": {…} | null }],
  "faqs":     [{ "question", "answer", "command": string | null }],
  "pillars":  [{ "word", "title", "text", "image": { "url", "width", "height", "alt" } | null }],
  "socials":  [{ "platform", "label", "handle", "url", "note", "blurb" }],
  "board":    [{ "name", "role", "photo": { "url", "width", "height", "alt" } }],
  "settings": { "tagline", "description", "about" } | null,  // null until first saved: the landing keeps its fallback
  "news":     [{ "slug", "title", "summary", "body", "publishedAt", "cover": { "url", "width", "height", "alt" } | null }],
  "commands": [{ "id", "command", "description", "output" }],
  // Social proof, appended after every other key (additive, see below)
  "sponsors":     [{ "name", "logo": { "url", "width", "height", "alt" }, "url": "https://..." | null }]
}
```

- `schemaVersion` (constant `PUBLIC_CONTENT_SCHEMA_VERSION`, `src/interface/public/public-content.mapper.ts`) is an integer that starts at 1 and is bumped **only on a breaking change** (a field removed, renamed or retyped). Adding fields never bumps it, so a consumer can refuse a version it does not know. `version` is the older name of the same value and is kept so existing consumers keep working: **the landing's validator reads `version`, not `schemaVersion`** (`src/lib/admin-content/validate.ts` in the landing repository rejects any value other than the one it knows), so never drop or change it on its own.
- `datePrecision` is `"day"` or `"month"`. `date` is always a full `YYYY-MM-DD`; a month-only event emits the first of its month (`2026-02-01`) with `"month"`. `YYYY-MM` is never emitted (the landing rejects it). Additive to `version` 1.
- `registration`, `calendarUrl` and `structuredData` on each event are additive to `version` 1 (S8; a landing built against an admin without them treats them as `null`): every previous event key keeps its value (`public-content-registration.mapper.test.ts` pins it). Their shapes are in "Event registration".
- `news` is additive to `version` 1 (a landing built against an admin without it treats it as `[]`): only published items, newest `publishedAt` first. `publishedAt` is a `YYYY-MM-DD` calendar date, `body` is the Markdown subset described in "News" (the landing must never render raw HTML from it), and `cover` is `null` when the item has none.
- **Social proof contract (S9).** `sponsors` is additive to `schemaVersion` 1 (a landing built against an admin without it treats it as `[]`; `schemaVersion` does not move). `impact` and `testimonials` used to travel here too and are no longer sent; a landing must treat their absence as `[]`. Only published, non-trashed items, in the order set in the admin (array order, no `sortOrder`). `sponsors[].logo` is always present (a sponsor cannot be published without one) and `url`, when not `null`, is an absolute https URL to wrap the logo in; with `null` render the logo without a link. Text is plain text, never HTML. The contract is built by `toPublicSocialProof` (`src/interface/public/public-social-proof.mapper.ts`, types in `public-social-proof.dto.ts`) and pinned key by key by its unit test; the route appends the list after the existing keys, so the pre-existing document is byte-identical (`public-content-get.test.ts` proves it).
- Image URLs are the Cloudinary `secure_url` as stored (`https://res.cloudinary.com/<cloud>/image/upload/v<n>/aso-computacion/events/<id>.<ext>`), which is the shape the landing accepts; `cloudinary-media-storage.test.ts` pins that contract.
- Events come newest date first (undated last) with only their active photos in gallery order; news comes newest `publishedAt` first; every other list is in the order set in the admin. Order is the array order, so there is no `sortOrder`.
- Nothing internal leaves: no ids (the event `slug` is the landing's stable id), storage `publicId`s, timestamps or publish flags. The board exposes **only name, role and photo** (S4). News exposes only its slug, texts, date and cover. The mapper builds each object key by key and `public-content.mapper.test.ts` pins every key set.
- `Cache-Control: public, max-age=0, s-maxage=5, must-revalidate`: the edge may collapse a burst of reads for 5 s but never serves a stale copy, because the landing rebuilds right after an edit and must see it.
- `ETag`: a strong validator (quoted SHA-256 of the serialized body). `generatedAt` changes on every read, so it is **left out of the hash**: the ETag changes exactly when the content does. A request with a matching `If-None-Match` (weak comparison, list or `*`) gets `304 Not Modified` with no body and the same `ETag`, `Cache-Control`, `Vary` and CORS headers.
- The 5 s `s-maxage` must stay **below** the deploy-hook debounce (`DEPLOY_HOOK_DEBOUNCE_MS`, 8 s): otherwise a build fired by the hook could read a copy from before the edit. Both constants carry a comment about it and a test pins it.
- CORS: `PUBLIC_CORS_ORIGINS` is an allowlist of exact origins (`https://host[:port]`; plain `http` only for `localhost`/`127.0.0.1`). The request's origin is echoed only when listed, never `*`, always with `Vary: Origin`; an entry with a path, wildcard or trailing slash is ignored and logged once. `OPTIONS` answers the preflight. No credentials are ever allowed.
- Rate limit: 60 requests per minute per client, 429 beyond that. **Best effort only**: the counters live in the memory of one serverless instance, so they are not shared between instances and reset when one is recycled. It stops a single client hammering a single warm instance and nothing more. The real protection is the CDN cache (`s-maxage`): repeated reads are answered at the edge and never reach Postgres. The map of clients is bounded (swept once per window, at most 10 000 tracked, oldest evicted first).
- Errors: any failure answers a generic `503 {"error":"Service unavailable"}` with `Cache-Control: no-store`; the cause is only logged on the server.
- Image URLs (`photos[].url`, `pillars[].image.url`, `board[].photo`, `news[].cover.url`, `sponsors[].logo.url`) are Cloudinary delivery URLs, so they contain the cloud name and the asset's `publicId` in the path. Both are public by design (they are needed to display the image) and neither lets anyone upload, change or delete anything; it is the API key and secret that must stay private. Do not treat these URLs as unguessable: an unpublished image whose URL leaked stays reachable until its asset is destroyed.

## Scheduling and preview

Events and news (the content with an editorial timeline) have an optional **publish window**; the other published entities (FAQ, pillars, socials, board, commands) are unchanged and have none.

**Window.** `publishAt` and `unpublishAt` are nullable instants (UTC, `TIMESTAMP(3)`; a `CHECK` requires `unpublishAt > publishAt` when both are set). `isPublished` stays the master switch: a draft is never public, whatever its window. For a published item:

| Moment `now` | State | On the public API |
|--------------|-------|-------------------|
| `now < publishAt` | Programado (scheduled) | hidden |
| `publishAt <= now < unpublishAt` (a missing end is open) | live | shown |
| `now >= unpublishAt` | Vencido (expired) | hidden |

`publishAt` is **inclusive** (visible from that exact millisecond) and `unpublishAt` is **exclusive** (hidden from that exact millisecond). The window is judged on every request to `/api/public/content` (`src/domain/publication-window.ts`); an item with no window is served exactly as before, and the response shape is unchanged (no window field is exposed). Not to be confused with `news.publishedAt`, the calendar date the landing shows.

**Forms.** The event and news forms have "Publicar el" and "Retirar el" (`datetime-local`). They are Ecuador time (America/Guayaquil, UTC-5 all year, no daylight saving), converted without using the server's own zone. Blank clears an end; a form that does not send the field leaves it alone. The lists show "Programado" (with the opening time) or "Vencido" (with the closing time) next to a published item that is not on the site right now.

**Preview.** The admin no longer has a screen to generate codes (`/admin/vista-previa` redirects to `/admin`); the endpoint `GET /api/public/preview` and the token format are unchanged, and `preview.token_create` stays in the audit log's history (validity was 1 hour, 24 hours or 7 days). It is a stateless HS256 token signed with `PREVIEW_TOKEN_SECRET`, so it cannot be revoked before it expires: rotate the secret to invalidate every token at once. It is shown once and kept nowhere.

`GET /api/public/preview` (a separate path, so no cache ever mixes the two) returns the same document as `/api/public/content` plus `"preview": true`, and includes drafts and scheduled items of every entity (an expired item stays out). One difference: the social-proof list (`sponsors`) is appended only by the content route, so the preview document has no `sponsors` key (`app/api/public/preview/route.ts` builds it from `toPublicContentResponse` alone); a landing must treat its absence as `[]`, as it already does for the normal document. It needs the header `X-Preview-Token: <token>`:

- No token, an expired or forged one, or no `PREVIEW_TOKEN_SECRET`: `401 {"error":"Invalid or expired preview token"}`, `Cache-Control: no-store`, and no content is read.
- A valid token: `200`, `Cache-Control: private, no-store`, no `ETag`, no CORS (it is meant for a server-side preview build of the landing, not for a browser).
- The token is read from the header only (never the URL or a cookie), never logged, and the Sentry scrubber drops the header. It shares the public rate limit (a guessing client gets `429`).

**Cron.** A static landing only shows scheduled content once it is rebuilt after the boundary, so `vercel.json` calls `GET /api/cron/scheduled-rebuild` once a day at 06:00 Ecuador time (`0 11 * * *` UTC), the most the Vercel Hobby plan allows. It reads `DeployStatus.lastSuccessAt` (when the deploy hook last accepted a call, from an edit or from the cron itself; a failed attempt does not overwrite it) and POSTs the deploy hook only if a **published, non-trashed** event or news item opened or closed in `(lastSuccessAt, now]`. Nothing changed: no build (`{"crossed":0,"outcome":"not-needed"}`). It requires `Authorization: Bearer <CRON_SECRET>` (Vercel adds it) and answers 401 otherwise, including while `CRON_SECRET` is unset or shorter than 32 characters (it fails closed). Answers: 200 `triggered` / `not-needed` / `disabled` (no `CLOUDFLARE_DEPLOY_HOOK_URL`), 502 `failed` (the hook refused, so the cron shows red in Vercel), 500 on an unexpected error. On Hobby, scheduled content therefore appears up to ~24 h after its time (plus the landing's build time) unless someone triggers a publish or a rebuild manually; on Pro, set the schedule back to `*/15 * * * *` for about 15 minutes.

The same route also runs the **registration retention** (see "Personal data and retention" in "Event registration") as an independent second step and the **registration reminders** (see "Reminders" in "Event registration") as a third, so the project needs no second cron. The body is `{"rebuild": {"crossed":N,"outcome":...}, "retention": {"deleted":N}, "reminders": {"sent":N,"failed":N,"events":N,"stoppedBy":"done"|"budget"|"time"|"provider"|"not_configured"}}`; a step that threw shows `{"error":"Service unavailable"}` in its place and the status is 500 (502 when only the hook refused). Whatever one step does, the others still run. The route's `maxDuration` is 60 s (it was 30): the reminders send up to the day's mail budget in this one run, and the reminders stop starting sends 45 s after the route began.

**Contract for the landing.** The landing implements it (variables `PREVIEW_BUILD`, `PREVIEW_TOKEN`, `ADMIN_PREVIEW_URL`; see its `docs/DEPLOY.md`, "Preview builds"). For the normal build nothing changes: keep reading `/api/public/content`. For a preview build, fetch `GET <admin>/api/public/preview` **server-side** with the header `X-Preview-Token` (token in a build secret, never in the page or URL), expect `preview: true` and the same shape and `schemaVersion`, never cache or deploy that build publicly, and treat `401` as "token invalid or expired: stop the build". The landing must not receive or compute windows itself.

## Event registration

Each event chooses how people sign up, in the "Inscripción" section of its form (`registrationMode`):

| Mode | Who | Data stored | Where |
|------|-----|-------------|-------|
| `none` (default) | nobody | none | no registration; capacity and deadline are cleared |
| `unl` | a signed-in **forum member** (verified `@unl.edu.ec` Google account, the same identity as the forum) | the member's name and email, as the forum holds them | `/inscripciones/<slug>` on this admin |
| `open` | anyone, no session: the form on `/inscripciones/<slug>` | name, email (**verified by a link, see below**), institution, and optionally career and semester (1 to 12) | `POST /api/public/events/<slug>/registrations` |

Optional **seats** (`registrationCapacity`, 1 to 5000, blank is unlimited) and **deadline** (`registrationDeadline`, Ecuador time, blank means "until the event day is over"). Both are enforced for both modes by one decision, `registrationRefusal` (`src/domain/event-registration.ts`), in this order: the event is not public now (draft, scheduled, expired, trashed, unknown) → `not_found`; the person is using the other mode → `mode_mismatch`; the deadline passed (`now >= deadline`) or the event day (exact dates only) is over in Ecuador → `closed`; this email is already registered **and confirmed** → `duplicate`; the seats (confirmed registrations only) are used → `full`. The Prisma adapter takes `SELECT … FOR UPDATE` on the event row and runs that same decision inside the transaction that inserts, so two people racing for the last seat, or one email sent twice at once, cannot both get in (`event-registration-prisma.repository.integration.test.ts`; taking the lock out makes those tests fail). Lowering the seats below the number already registered just closes registration; nobody is removed. **The admin is asked first (D14):** a save that changes the mode, or sets the seats below the **confirmed** registrations while lowering the limit in force (lifting it, raising it or keeping one already below the count asks nothing; a pending registration holds no seat and is not counted), is a change `registrationChangeImpacts` (`src/domain/event-registration.ts`) reports. The edit form (`app/admin/events/_components/event-form.tsx`, told the count by `getAdminEvent` as `registeredCount`) then asks, before anything is sent, "Este evento ya tiene N inscritos." plus what happens to them (`src/interface/admin/events/registration-change.ts`: the registered keep their seat; switching registration off keeps them but takes the event out of the registrations list and stops their reminder; below the count the event is full and nobody loses a seat), with «Guardar el cambio» and «Seguir editando». Accepting sends the save with `confirmRegistrationChange=on`; the server action (`updateEvent`, `registration-change-guard.ts`) reads the current mode and the confirmed count and, **without that exact flag**, answers `{ error }` with the same question and stores nothing (no audit, no rebuild): a draft's autosave never carries it, so it shows that message and the Save button asks. A save that sends no mode or seats reads nothing.

**One registration per person and event**: `UNIQUE (eventId, email)` with the email lower-cased (`CHECK`). A repeat attempt for a **confirmed** registration changes nothing: the first one stays as it was. A repeat while the first is still **pending** refreshes that same row (same id, new data, a new 48 h window) and sends the link again, **and only that newest link works** (D9): each registration attempt stores a new random `confirmNonce` on the row (column added by the migration `20261109120000_registration_confirm_nonce`; never part of the record the admin lists, exports or the repository returns) and signs it into the link as `nce`; the link of the earlier email names the old nonce and is `invalid`.

**Email confirmation (`open` mode).** The open form proves the address before a seat is taken (decision: "el cupo cuenta al confirmar"). The `POST` stores the registration **pending** (`confirmedAt` empty) and emails a link to `/inscripciones/<slug>/confirmar?token=…`. A pending row takes no seat and is not counted, listed, exported or seen by `exists`: `EventRegistrationRepository.count / countByEvents / exists / list` read confirmed rows only (`confirmedAt IS NOT NULL`), so nobody can block seats with fake emails. UNL rows are born confirmed (the `CHECK` `EventRegistration_unl_data_check` also refuses an institution or a missing `confirmedAt` on them); `reminderSentAt` may only be set on a confirmed row. The token is a `jose` HS256 JWT signed with `REGISTRATION_CONFIRM_SECRET` (own secret, never `ADMIN_SECRET` or `FORUM_SESSION_SECRET`), claims `purpose: "registration-confirm"`, `rid` (registration id), `eid` (event id), `nce` (the attempt's nonce, absent on a link sent before the column existed), valid 48 h (`src/infrastructure/registration/registration-confirm-token.ts`). The page shows the event and a **Confirmar mi cupo** button; the button `POST`s to `/api/public/events/<slug>/registrations/confirm` (**never confirmed on GET**: mail scanners and link previews open every link). `EventRegistrationRepository.confirm` takes the same event row lock as `register` and applies the same decision: a seat that went to others meanwhile answers `full`, a closed event `closed`, and either leaves the row pending. A registration older than 48 h (counted from its last refresh) is `expired`; an unknown id, a link used on another event or the link of an earlier attempt (the same email registered again, D9: the row only answers to the nonce it holds now, confirmed or pending, and a refusal changes nothing) is `invalid`; a pending row from before the column (no nonce) is confirmed by a link that carries none, until it expires or its email registers again; an already confirmed one is `already_confirmed` and changes nothing. The 48 h window and everything else about it are in `src/domain/event-registration.ts` (`REGISTRATION_CONFIRMATION_TTL_MS`, `isConfirmationExpired`).

**UNL mode.** `registerForEvent(slug)` (`src/interface/forum/event-registration.ts`) starts with `requireForumMember()`: only a `forum_sid` passes, never an admin one, and a suspended member's session is already refused. It takes **no data from the caller**; the name and email come from the member row, and the email domain is checked again against `FORUM_ALLOWED_EMAIL_DOMAIN` (unset refuses everyone). The page `/inscripciones/<slug>` shows the event, the state (open, full, closed, already registered) and, for a visitor, a link to the forum's Google login, or, when that login is not configured on this server (`isForumEnabled()` is false: `loginAvailable` of `getEventRegistrationPage`), "La inscripción con cuenta UNL no está disponible en este momento" instead of a sign-in that would end in an error (someone already signed in can still reserve). A visitor's sign-in link carries `?next=/inscripciones/<slug>` (`app/inscripciones/[slug]/page.tsx`), so after the Google login the student comes back to the event page (see "Return path" in "The forum is a separate zone"). A sign-in that began there also *fails* back there: `forum-google-login.ts` redirects to the page with `?error=<code>` (a suspended account gets the generic `denied`), and the page tells it in registration words (`login-problems.ts`). The action's own refusals use registration wording too (`src/interface/event-registration/registration-action-errors.ts`: "Su sesión terminó…", "Su cuenta no puede reservar cupos…"), never "participar en el foro" (D5); after a gone session the button offers the sign-in back to the same page.

**The event page** (`/inscripciones/<slug>`, `app/inscripciones/[slug]/`) is the one place to register for any event, and it is public. It has its own layout (`app/inscripciones/layout.tsx`: the shared `AppTopBar` named "Inscripciones" whose brand leads to the list, the theme toggle, one reading column; no "Foro" anywhere) and its own stylesheet (`inscripciones.css`, which holds the paper pass both of its screens are drawn with: the event `.ticket`, the list's `.reg-card` and the sign-in `.pass`); it shares nothing with the forum's shell, rail or `forum.css`. It was born under `/foro/eventos/<slug>` and moved out on 2026-11-07: `next.config.ts` answers a permanent redirect (`308`) from `/foro/eventos/<slug>` to `/inscripciones/<slug>` keeping the query string (`REGISTRATION_REDIRECTS`, `src/infrastructure/http/registration-redirects.ts`), so links already shared keep working; `/foro/eventos` (the old list, which was the forum's) redirects `308` too, to `/inscripciones`, from `app/foro/eventos/page.tsx` (`permanentRedirect`, query string kept). The proxy matcher reaches the page only for the undecodable-path check (a malformed percent escape answers `400`) and the forum cookie migration, and never guards it (only `/` and `/admin/*` are guarded); it reads the session without requiring it, so only the part that needs a member asks for one. The Google sign-in is still the forum's (`/foro/auth/google/*`, so Google's redirect URI did not change) and `parseForumReturnPath` accepts `/inscripciones/<slug>` as a return path. `getEventRegistrationPage(slug)` (`src/interface/forum/event-registration-read.ts`) picks the page by mode, `404` for an unknown or non-public event: the event is always drawn as a ticket (`event-ticket.tsx`): a red date stub, the title, hour and place, the seats ("Quedan N cupos" with a meter, only when the event has a limit; `Inscripciones abiertas`, `Cupos agotados` or `Inscripciones cerradas` over the ticket; the page is never prerendered) and, under the perforation, a navy tear-off that holds the one action of the mode. `unl`: one quiet line and the Google button (the same pass language as the registrations sign-in), then, for a signed-in member, a single "Reservar mi cupo" and the member's name; once registered it says so and offers the `.ics`. `open`: the form (nombre, correo, institución, carrera y ciclo opcionales, Turnstile, privacy note) and "Reservar mi cupo", replaced by the state when the event is full or closed, and by "Revise su correo" once the link has been sent (no seat is taken yet, so no calendar and no refresh); the confirm page (`/inscripciones/<slug>/confirmar`, same ticket, a "Confirmar mi cupo" button) shows "Listo, su cupo está reservado" with the `.ics`, "Su cupo ya estaba reservado", "Cupos agotados", "Las inscripciones cerraron", or, for an expired or unusable link, a message with a link back to the form; for an event that no longer takes open-form registrations (switched to another mode, unpublished or trashed) a valid or expired link gets "Este evento ya no recibe inscripciones" with a link to `/inscripciones` instead of a 404 (D11; a bad token on a public event says "Este enlace no sirve", and an unknown event with a bad token stays a 404). `none`: "Entrada libre" on the ticket and, in the tear-off, the *pase libre* notice with the event's `.ics` when it has an exact upcoming day. **The list** (`/inscripciones`, `app/inscripciones/page.tsx`) is public and reads no session: one ticket-style card per event that takes a registration now, UNL or open (`ListOpenRegistrationEventsUseCase`: visible, mode not `none`, `registrationState` open; seats from one aggregated query; soonest first, undated last), with "Con cuenta UNL" or "Abierta al público", the live seats and a link to the event; the empty state is "No hay inscripciones abiertas." A failed read is an error page, not an empty list. The form (`open-registration-form.tsx`) checks the fields in the browser with the domain's own rules (`src/interface/event-registration/open-registration.ts`), then `POST`s to the public endpoint below, same origin, so every server rule (rate limit, 4 KB body, Turnstile, unique email, race-safe capacity, Ecuador-time deadline) applies unchanged. Each answer is shown where the person is looking: `validation` and `duplicate` on their field (`aria-invalid` and focus), `full`, `closed` and `not_found` replace the form, and `rate_limited`, `captcha`, `unavailable`, `email_unavailable`, `email_budget` and network errors go in one alert that keeps what was typed. All of its copy is addressed as usted.

**Open form.** The endpoint is public by design (`route-protection.test.ts` lists it). In order, cheapest first: rate limit (5 attempts per client per 10 minutes, `429` + `Retry-After`; best effort per instance like the read limiter), request shape (`Content-Type: application/json`, at most 4 KB read as a stream, a JSON object; `415` / `413` / `400`), **Turnstile** (`turnstileToken` verified server-side with `TURNSTILE_SECRET_KEY`; `400 {"error":"captcha"}` for a missing or rejected token; `503 {"error":"unavailable"}` when Cloudflare cannot be reached, the secret is wrong, or in production there is no secret: **fail closed**), then strict validation (a bad field is a `400` even while mail is down), a check that an email can go out (**before** anything is stored), the atomic decision, and the confirmation email. Fields (extra keys are ignored): `name` 1–120, `email` valid and at most 254, `institution` 1–120, `career` 1–120 (optional), `semester` integer 1–12 (optional); no control characters. Answers never echo what was sent and are `Cache-Control: no-store`:

| Status | Body | Meaning |
|--------|------|---------|
| 201 | `{"ok":true,"confirm":"email"}` | stored pending and the confirmation link was sent; no seat is taken yet |
| 400 | `{"error":"validation","field":"semester"}` / `{"error":"captcha"}` / `{"error":"bad_request"}` | invalid field, Turnstile failed, malformed JSON |
| 404 | `{"error":"not_found"}` | no such public event, or it does not use the open form |
| 409 | `{"error":"duplicate"}` / `{"error":"full"}` / `{"error":"closed"}` | already registered, no seats, deadline or event day passed |
| 413 / 415 / 429 / 503 | `{"error":"too_large"}` / `unsupported_media_type` / `rate_limited` / `unavailable` | |
| 503 | `{"error":"email_unavailable"}` | no confirmation email can go out: Gmail or `REGISTRATION_CONFIRM_SECRET` or `AUTH_URL` not set, or the provider refused. Nothing is stored for the first reasons; after a provider failure the pending row is left (a retry refreshes it) and the daily budget unit is given back |
| 503 | `{"error":"email_budget"}` | today's mail budget (`MAIL_DAILY_LIMIT`, Ecuador day) is spent; nothing is stored. Try again tomorrow |

**Confirm endpoint.** `POST /api/public/events/<slug>/registrations/confirm` with `{"token":"…"}` (JSON, at most 2 KB). Same-origin (no CORS), no Turnstile (the signed token is the credential), `Cache-Control: no-store`, its own budget of 5 attempts per client per 10 minutes (`429`). There is no `GET`. Answers: `200 {"ok":true,"status":"confirmed"|"already_confirmed"}`; `409 {"error":"full"|"closed"}` (the row stays pending); `410 {"error":"expired"}` (the token, or the stored registration, is older than 48 h); `400 {"error":"invalid"}` (missing, forged, another event's, unknown registration, or the link of an earlier attempt: only the latest link of an email works); `404 {"error":"not_found"}` (not a slug, unknown, or not public now); `413 / 415 / 400 bad_request`; `503 {"error":"unavailable"}`.

CORS is the read API's allowlist (`PUBLIC_CORS_ORIGINS`, exact origins, no credentials); the preflight answers `POST, OPTIONS` and `Content-Type` only to a listed origin. The only form that posts here today is the admin's own event page, same origin, so no entry is needed; the landing has no form (it links to the event page and only reads the seats). Any client of this endpoint must now send `institution` (a client that does not gets `400 validation` on `institution`) and read `201` as "check your email", not "seat reserved". A duplicate answer does reveal that an address is already registered **and confirmed** for that event; nothing else about a person is ever returned.

**Calendar file.** `GET /api/public/events/<slug>/calendar.ics` is public (no session, no personal data), rate limited and CORS-allowlisted like the content API, `Cache-Control: public, max-age=0, s-maxage=60, must-revalidate`, `Content-Disposition: attachment`. It exists only for an event that is public now and has an exact day (`404` otherwise). Times come from the first readable `HH:MM`, `HHhMM` or `Hh` in the free-text `hora` (the next one, if later, is the end); with none it is an all-day event. Times are written in UTC (Ecuador has no daylight saving, so no `VTIMEZONE`), text is escaped and lines are folded at 75 octets per RFC 5545. A start without an end has no `DTEND`. `UID` is `<slug>@aso-computacion` (no internal id).

**Live seats.** `GET /api/public/events/seats` tells the landing how many seats each event has left, at page load, without a rebuild. It lists every event that takes registrations (`unl` or `open`) and is public now (published, inside its publication window, not trashed), at any date, soonest first and undated last. Read-only and **PII-free**: only the slug and counts; no ids, names, emails or titles.

```jsonc
{ "events": [
  { "slug": "taller-de-git", "capacity": 60, "registered": 48, "seatsLeft": 12, "status": "open" },
  { "slug": "charla-abierta", "capacity": null, "registered": 3, "seatsLeft": null, "status": "open" },
  { "slug": "hackathon", "capacity": 2, "registered": 2, "seatsLeft": 0, "status": "full" }
] }
```

- `registered` counts the **confirmed** registrations, whatever the mode (a pending open-form registration takes no seat and is not counted). `capacity` and `seatsLeft` are `null` when the event has no limit; `seatsLeft` is never below 0.
- `status` is `registrationState` (`src/domain/event-registration.ts`), the same rule the registration applies: `closed` when the deadline instant has passed or the event day is before today in Ecuador; else `full` when `registered >= capacity`; else `open`. `closed` wins over `full`. A month-only or undated event never closes by date.
- One aggregated query counts all events (`EventRegistrationRepository.countByEvents`, a `GROUP BY`), never one per event.
- `Cache-Control: public, max-age=0, s-maxage=5, must-revalidate`, like the content API. Rate limit: the read API's (60 per minute per client, 429 + `Retry-After`). Any failure answers a generic `503 {"error":"Service unavailable"}` with `no-store`.
- CORS: `Access-Control-Allow-Origin: *` (no credentials, no cookies are read), because the answer holds no personal data and a landing preview on a new origin must work; `OPTIONS` answers `204` for `GET`. It does **not** use the `PUBLIC_CORS_ORIGINS` allowlist, which stays for the content API and the registration form.
- The number is a hint for the UI. The server stays the authority: the registration itself still answers `full` / `closed`.

**Public API, per event** (additive; `null` when it does not apply):

```jsonc
"registration": {
  "mode": "unl" | "open",
  "capacity": 40 | null,
  "deadline": "2026-11-27T23:00:00.000Z" | null,   // exclusive, UTC
  "url": "https://<admin>/inscripciones/<slug>" | null,                        // unl only
  "endpoint": "https://<admin>/api/public/events/<slug>/registrations" | null // open only
} | null,
"calendarUrl": "https://<admin>/api/public/events/<slug>/calendar.ics" | null,
"structuredData": {                                // values for a schema.org Event, Ecuador time
  "startDate": "2026-11-28T09:00:00-05:00",        // or "2026-11-28" when the time is unknown
  "endDate": "2026-11-28T11:00:00-05:00" | null,
  "location": "Laboratorio 2" | null,              // the event's `lugar`
  "registrationUrl": "https://<admin>/inscripciones/<slug>" | null   // `unl` only; null for `open`, whose page the landing derives from the admin origin
} | null
```

URLs are built from `AUTH_URL` and are `null` while it is not set. `structuredData` and `calendarUrl` are `null` for a month-only or undated event. The seats left are **not** in the content snapshot (they change with every registration and the landing is static): `capacity` is the total, the live count is `GET /api/public/events/seats` (below), and the registration endpoint answers `full` / `closed` when it is too late. For the JSON-LD the landing adds `@type: "Event"`, `name`, `description`, `image`, `eventAttendanceMode` and, when registration exists, `offers: { "@type": "Offer", url, price: "0", priceCurrency: "USD", availability }`, where `url` is the event page `<admin origin>/inscripciones/<slug>` for both modes (the landing reads the origin from `registration.url` or, for `open`, from `registration.endpoint`; `open` sends no page URL).

**Admin overview.** `/admin/registrations` (the «Inscripciones» area of the rail and the phone's tab bar) gathers every event that takes registrations (`unl` or `open`), at any date: **upcoming first** (soonest first; an event with only a month counts as upcoming until the month is over, an undated one goes last), then **past** (most recent first). Each row shows title, date, mode, `registered / capacity` (or `n · sin límite`), the deadline (or "Con el día del evento"), the state (`Abierta`, `Sin cupos`, `Cerrada`, from the same `registrationState` as the public seats) and a **Ver inscritos** link to that event's page above. Unlike the public endpoint it also lists drafts, scheduled and withdrawn events, saying so under the title. **ADMIN and EDITOR** can open it, like the per-event page; it shows counts only, never a name or an email. The read (`getAdminRegistrationOverview`) starts with `requirePageSession()`, the route sits under the `/admin/:path*` proxy matcher, and the counts come from one grouped query (`ListRegistrationOverviewUseCase`).

**Admin.** `/admin/events/<id>/registrations` lists the confirmed people, with their institution (linked from the event editor): **ADMIN and EDITOR** can view; only an **ADMIN** can export (`GET /admin/events/<id>/registrations/export`, a UTF-8 CSV with a byte order mark (columns: Nombre, Correo, Forma de inscripción, Institución, Carrera, Ciclo, Inscrito el), every cell quoted, spreadsheet formulas neutralised with a leading `'`; `401` / `403` / `404` as statuses) or delete a registration (`deleteEventRegistration`, `requireRole("ADMIN")`, a row in `action-policy.ts`). Both are audited (`event.registrations_export`, `event.registration_delete`) with the event id and, for the export, a count: **never a name or an email** in a summary. Deleting is permanent and frees the seat.

**Reminders.** Every confirmed registrant, from the open form and from the UNL Google sign-in alike, gets one email a few days before the event (decision: "entre 3 y 1 día antes, repartido"). The daily cron's third step (`runRegistrationReminders`, `SendRegistrationRemindersUseCase`) selects the **public** events (published, inside their publication window, not trashed; `registrationMode` not `none`) with an **exact day** that is one to three days ahead in Ecuador (`reminderWindow`, `src/domain/registration-reminder.ts`; today and past days are out), **nearest event first**, and for each the confirmed registrations with `reminderSentAt` empty, oldest first. It sends up to what is left of **its share** of the day's mail budget (the same `MailDailyCounter` the confirmations spend from) and stops when the share is gone: at most 70 % of the cap (`REMINDER_SHARE_OF_DAILY_MAIL`, rounded down: 280 of 400; `reminderMailAllowance`, `src/domain/registration-reminder.ts`), counting every message already sent that day, so confirmations keep the rest (D12) and may still use all of it, so what does not fit goes out the next day, still nearest first; because an event stays in the window until the day before, a person is reached at the latest the day before as long as the day's budget covers the nearest events. `reminderSentAt` is written only **after** the send succeeded (`markReminderSent`, one conditional `UPDATE`), so a failed send stays due for the next run, and running the step twice sends nothing twice. Three failed sends in a row end the run for the day (`stoppedBy: "provider"`: the provider is down, not the addresses); a send the provider refused gives its budget unit back. The run also stops starting sends 45 s after the route began (`stoppedBy: "time"`, `REMINDER_TIME_BUDGET_MS`); it sends on one pooled SMTP connection (about 0.2 s a message), so roughly 150 reminders fit, and the rest follow the next day. Without the Gmail account or `AUTH_URL` it sends and records nothing (`stoppedBy: "not_configured"`). The email (`reminderEmail`) holds the title, the date and time, the place, the link to `/inscripciones/<slug>` and the `.ics` link, and nothing the person typed. The UNL page promises the reminder only while mail is set up (`remindersOn`).

**Personal data and retention.** Registrations are personal data, kept only for the people who signed up for that event: nothing is shared, there is no analytics on them, and the CSV is the only way out. They are deleted with their event (`ON DELETE CASCADE`, i.e. when it is deleted for good from the trash), one by one by an ADMIN, or **automatically 90 days after the event ends** (decision: "90 días y se borran solos").

The retention rule (`src/domain/event-registration-retention.ts`):

- **When an event ends.** At the end of its `date`, a calendar day in Ecuador time. With `datePrecision: "month"` the day is unknown, so the event ends with the **last day of that month**. An event **without a date never expires**: nothing says when it ended, so its people are kept until an ADMIN removes them or the event is deleted.
- **When they are deleted.** Once 90 full days have passed since that moment, **inclusive**: an event on 2026-01-10 ends at 2026-01-11 00:00 (Ecuador); its registrations are kept up to and including 2026-04-10 and are deleted by the first run at or after 2026-04-11 00:00 Ecuador (05:00 UTC). Events that are newer, in the future or undated are not touched, and neither is any other table: only `EventRegistration` rows are deleted, never the event, its photos or anything else. Trashed events count too.
- **How.** The daily cron (see "Cron" in "Landing rebuilds") runs it as its own step, independent of the rebuild: a failure in one never blocks the other. It deletes in batches of 500 rows, at most 20 batches per run (10 000 rows); a bigger backlog finishes on the next day's run. Running it twice deletes nothing the second time.
- **Audit.** Each run that deleted something writes one `event.registration_purge` entry by the system with the **count only** (no names, emails or event titles). If a run fails after deleting some rows, those are audited too. A run that deleted nothing writes nothing.
- **Cadence.** Because the cron runs once a day, a registration is deleted between 0 and 24 hours after the 90-day mark.
- **Unconfirmed emails.** A pending open-form registration (email never confirmed) is deleted by the same run once its 48 h window is over (`deleteStalePendingBatch`, whatever its event; they hold a stranger's name and email for nothing). They count in the same audit total.

## Email

Mail goes out through a `MailSender` port (`src/application/ports/mail.ports.ts`) that knows nothing about the provider. `BudgetedMailSender` (`src/application/mail/`) is the only implementation: every send first reserves one unit of the Ecuador day's budget and then calls a `MailTransport`; the Gmail SMTP adapter (`src/infrastructure/mail/gmail-smtp-transport.ts`, nodemailer, SMTPS to `smtp.gmail.com:465` with an app password, 10 to 15 s timeouts; the test-only `MAIL_SMTP_*` can swap the server for the e2e sink) is the only code that knows Gmail, so moving to a service with an own domain replaces that adapter and nothing else. The budget is the table `MailDailyCounter` (`day` `YYYY-MM-DD` in Ecuador, `sent`): reserving is one atomic `INSERT … ON CONFLICT DO UPDATE … WHERE sent < limit`, so no number of instances or callers goes past `MAIL_DAILY_LIMIT`; a send the provider refuses gives its unit back. Results are `sent`, `not_configured`, `budget_exhausted` and `failed`. The configuration reader (`src/infrastructure/mail/mail-config.ts`) mirrors the forum's: placeholders, short secrets and a secret equal to another are treated as unset, and `mailConfigProblems()` lists variable names only. The emails themselves (`src/interface/event-registration/registration-emails.ts`) are Spanish, addressed as usted, and carry nothing the registrant typed, so a stranger's address cannot be made to deliver text of someone else's choosing.

## Landing rebuilds

Every successful admin mutation (events and their photos, news, FAQ, commands, pillars, socials, board, sponsors, settings, and the bulk and reorder actions) calls `requestSiteRebuild()` after the write, which POSTs `CLOUDFLARE_DEPLOY_HOOK_URL`. It is best effort: it only schedules, never awaits the network and never throws, so it cannot fail or slow the mutation. A failed mutation never fires it (`deploy-hook-actions.test.ts` checks all 44 actions of the events, FAQ, commands, news, pillars, socials, board and settings modules: fired once after the write, not fired on failure or without a session; the sponsor, bulk and reorder actions have their own tests).

- **Coalescing.** A trailing debounce: each call restarts an 8 s quiet window and the hook is POSTed once, 8 s after the last edit, but never later than 15 s after the first edit of the burst (max wait), so a long editing session cannot keep the invocation open past `maxDuration`. Reordering photos or editing several fields is one build, not one per click. The window is longer than the 5 s edge cache of the public route, so the build reads fresh data. The POST has a 5 s timeout; failures and non-2xx answers are logged as warnings (without the URL).
- **Why in process, and the Vercel caveat.** No extra table or queue for a handful of editors. But state is per instance, and a serverless instance may be frozen between requests. So the action registers the wait with `after()` (from `next/server`), which keeps the invocation alive until the window has elapsed and the hook was called; `app/admin/layout.tsx` sets `maxDuration = 30` so an upload plus the longest wait (15 s) and the hook call (5 s timeout) fits. If an instance is still recycled mid-window, or two instances each debounce their own edit (two builds), the cost is a lost or duplicated rebuild, never a wrong page: the daily rebuild cron is the safety net. On a long-lived server (Render, `next start`) the timer simply runs.
- **Last deploy status.** Each attempt overwrites the single row of `DeployStatus` (id `landing`, enforced by a `CHECK`): when it ran, whether it succeeded, and the HTTP status or a coarse error kind (`timeout`, `network`). The hook URL is a secret and is never stored. The dashboard shows it as "Último despliegue: hace 3 min · OK" or "Último despliegue: Falló (HTTP 500) · hace 2 h" with a hint. **OK means Cloudflare accepted the request, not that the build finished.** Writing the status never fails the content action: a failure is logged (without the error text) and reported to Sentry. The age is computed when the page renders, so reload to refresh it. Nothing is shown if the read fails; "Aún no se solicitó ningún despliegue." appears until the first attempt.
- **Scheduled content** has its own trigger: the cron in "Scheduling and preview" rebuilds only when an item crossed its window since the last accepted call.
- **Drafts do not rebuild.** The update actions of events, FAQs, news, board, pillars, commands, sponsors and socials (and the create actions of the same eight) skip `requestSiteRebuild()` when the row was a draft before the save and stays a draft after it (autosave and the manual save alike), because the landing shows nothing of it. The decision is `shouldRebuildSite(wasPublished, isPublished)` in `src/interface/admin/site-rebuild-policy.ts`; `wasPublished` is the `wasPublished` the update use case reports from the stored row it already read, never anything the client sends. Publishing, unpublishing (published → draft) and any save of a published item rebuild as before, and a new item rebuilds only when it is created already published. The audit entry and `revalidatePath` do not change, so Historial still lists every draft save. The list switches (`set…Published`, bulk publish), reorder and photo/cover/logo actions are not covered by this rule and still rebuild; trash only rebuilds for a published item (above). Tests: `draft-save-rebuild.test.ts` (the eight actions) and `update-reports-published-before.test.ts` (the use cases).

## Login throttle

The login is throttled per client, in Postgres (table `LoginAttempt`), so the limit holds across Vercel instances; an in-memory map is per instance and N instances multiplied the allowed guesses by N.

- **Exponential backoff, not a lockout.** The first 5 attempts from an IP are free; after that the next attempt must wait 30 s, then 60 s, 120 s, 240 s, and 5 min at most. Attempts made while waiting are refused without counting, so hammering never extends the wait. After 1 hour without attempts the counter restarts, and the stale rows are purged.
- **Why not the old "5 failures, 15 minutes locked".** On a shared network (a campus NAT puts everyone behind one IP), anyone could lock the administrator out for as long as they liked. With a capped backoff the worst case is a wait of 5 minutes, and a different network (mobile data) is never affected. The correct password is *not* a way around the wait: a throttled IP is refused even with the right password, otherwise the throttle would answer guesses for free.
- **Known-device cookie.** A capped backoff alone still lets someone on the administrator's own network keep the IP at the cap forever (one attempt per 5 minutes is theirs to take). So a successful login also sets `admin_device`: a signed (same `ADMIN_SECRET`), `httpOnly`, `secure`, `sameSite=strict` cookie, valid for 180 days and renewed on every login, carrying a random device id. A login attempt with a valid `admin_device` is throttled in its own bucket (`device:<id>`) and ignores the IP bucket, so the attacker's attempts no longer reach the administrator. The device bucket has the same backoff, so a stolen cookie is not an unlimited guessing oracle, and a good login clears only the bucket it spent. A forged, expired or missing cookie falls back to the IP bucket. The cookie can never act as a session: it has another name and purpose claim and no `sub: "admin"`. The cookie is also bound to the current `ADMIN_PASSWORD` through a `pv` claim (a truncated HMAC of the password keyed with `ADMIN_SECRET`; it reveals nothing about the password), so rotating `ADMIN_PASSWORD` when the board changes makes every device cookie stop matching and those browsers fall back to the IP bucket until their next login. Rotating `ADMIN_SECRET` invalidates every device cookie (and every session). The first login from a new browser, or after clearing cookies, is still on the IP bucket.
- **IPv6 by /64.** An IPv6 client owns a whole /64, so the key is the /64 prefix (`2001:db8:1:2::/64`), not the address: rotating through the host part buys nothing. IPv4 and IPv4-mapped IPv6 addresses (`::ffff:a.b.c.d`) are keyed as they come.
- **Trade-off, no global ceiling.** A cap across all IPs would let any attacker lock the administrator out from everywhere, a worse failure than a neighbour on the same NAT. A botnet that rotates IPs is held back by the strength of `ADMIN_PASSWORD` (hence the 16-character minimum), not by this throttle.
- **Bounded exponent.** The doubling stops at 2^10, so a key held at the cap for days cannot overflow the SQL arithmetic; the wait itself is capped at 5 minutes anyway.
- **Atomic.** Each attempt is spent *before* the password is compared, in a single `INSERT ... ON CONFLICT DO UPDATE ... WHERE` statement, so 30 parallel guesses spend at most the 5 free attempts. A successful login deletes the row of the bucket it spent (the IP's, or the device's).
- **Fails closed.** If the throttle store cannot be reached, login is refused ("temporarily unavailable") instead of running unprotected; the error is logged. If `ADMIN_PASSWORD` is unusable (unset, placeholder or under 16 characters), login is refused the same way and an `ADMIN_PASSWORD is not set, is still a placeholder or is shorter than 16 characters` error is logged once per process (not per attempt).
- **The client IP** is `x-real-ip`, then the first `x-forwarded-for` entry (Vercel overwrites both). Without either header (local development, a bare `next start`) every request shares one `unknown` bucket: it is throttled like any other key, so it is safe, but everyone behind it slows each other down. A warning says so once per process.

## The forum is a separate zone

Students are **not** `User` rows. `ForumMember` / `ForumSession` and the other `Forum*` tables are independent of `User` / `Session`, and the forum has its own cookie, secret, claims and guard so that neither kind of session can ever pass the other's check:

- Cookie `forum_sid`, `path=/`, signed HS256 with `FORUM_SESSION_SECRET` (≥ 32 characters, refused when equal to `ADMIN_SECRET`). Claims `sid`, `mid`, `typ: "forum-session"`, `aud: "aso-computacion-forum"`, `sub = mid`; none of the admin's `kind` / `uid` / `role`. The admin session module, `hasValidClaims`, `requireSession` / `requireRole` and the proxy matcher are untouched; the admin cookie (path `/`) reaches `/foro` but the forum guard reads only its own cookie, and the forum cookie reaches `/admin` but the admin guard never reads it. **Migration from `forum_session` (path `/foro`):** until 2026-11 the cookie was `forum_session` on `/foro`, which the browser would never send to `/inscripciones/<slug>`. The proxy (`migrateLegacyForumCookie`, `src/interface/forum/migrate-legacy-forum-cookie.ts`) runs on `/foro`, `/foro/**` and `/inscripciones/**`: when a request carries the legacy cookie and not `forum_sid`, a legacy token that verifies is copied to `forum_sid` (same value, 7 days, `HttpOnly`, `SameSite=Lax`, `Secure` in production), the legacy cookie is expired (`Path=/foro; Max-Age=0`) and the current request already sees the new cookie, so nobody signs in again. A token that does not verify is expired and never copied; with no usable forum secret nothing is touched. Logout clears both. The legacy cookie is only ever sent to `/foro`, so a visitor holding only that one who lands straight on `/inscripciones/<slug>` looks signed out until any forum page is visited; the Google sign-in on the registration page still works.
- Guards: `requireForumMember()` (server actions, throws) and `requireForumPageMember()` (pages and reads, redirects to `/foro`) in `src/interface/forum/`. They fail closed (missing secret, bad cookie, revoked or expired session, suspended member, database error). Every student-facing action module starts each action with `requireForumMember()` (`forum-posting.ts`); the admin-side category actions are ordinary admin actions with `requireRole("ADMIN")` and a row in `action-policy.ts` (their screen is not built yet, see "The forum screens"). `hasSuspendedForumSession()` (`src/interface/forum/forum-suspension.ts`) is **not a guard**: it only picks the words `/foro` shows (the suspension notice instead of the sign-in). It is true only for the validly signed, unexpired `forum_sid` of a member whose status is SUSPENDED, also when the suspension already revoked that session; a missing, forged or expired cookie, no secret and any error answer false.
- Event registration with a UNL account lives at `/inscripciones/<slug>` (outside the forum, same session) with the `registerForEvent` action (`src/interface/forum/event-registration.ts`, guard first, no data taken from the caller). See "Event registration".
- Login: `/foro/auth/google/start` and `/foro/auth/google/callback` (own state cookie `forum_oauth_state`, path `/foro/auth/google`). `FORUM_ALLOWED_EMAIL_DOMAIN` is required (unset = login disabled); the email domain and `hd` must match and the email must be verified. A new valid identity becomes a member on the spot.
- Return path: `/foro/auth/google/start?next=<path>` brings the student back to `<path>` after a successful login. Only a same-origin path equal to `/foro`, under `/foro/` or under `/inscripciones/` (the event registration page; a slug is required) is accepted (at most 512 characters; no `//`, backslash, whitespace or control characters, encoded slash, backslash or percent, no dot segments out of those prefixes, nothing under `/foro/auth`); anything else is ignored and the login ends at `/foro`. The value is sealed in the `forum_oauth_state` cookie and re-validated on the callback, which never reads a `next` from its own URL. A refused or failed login still goes to `/foro?error=…`. A visitor opening a thread, a category page (with its `?pagina=`) or a category's new-thread page is sent to `/foro?next=<that path>`, and that page's sign-in link carries it; new pages can use `forumSignInHref` / `requireForumPageMember(returnTo)`. The admin login has no such parameter.
- No public DTO (`src/application/dto/forum-result.dto.ts`) carries an email, a Google id or a member id: other students are a display name, and "mine" is a boolean computed for the viewer.
- Posting is throttled per member in the database (`src/application/forum/posting-throttle.ts`); the refusal names the limit that was hit (3 per minute or 30 per hour) and the time really left in whole minutes, rounded up: until the oldest post inside the window that tripped leaves it (`ForumPostRepository.oldestPostSince`), not the whole window, and with both limits exceeded the longer wait (`ForumThrottledError` carries `retryAfterSeconds`, `max` and `per`; the action result has no `retryAfterSeconds`); a reply is written under the thread's row lock so a lock racing a reply cannot lose.
- Moderation (S10d): students report through `src/interface/forum/forum-moderation.ts` (member guard, one open report per member per post, decided by a partial unique index). The admin side is `src/interface/admin/forum/moderation-actions.ts`: **EDITOR-level** actions (`requireSession()`, rows in `action-policy.ts`) that hide or show a thread or reply, lock or unlock a thread, suspend or reactivate a member and close a report; each writes an audit entry with ids only, except a step that finds the target already in the wanted state (hiding a hidden post, reactivating an active member): it answers `{ success: true, unchanged: true }`, writes no entry and the queue still refreshes. Page: `/admin/foro/reportes` (`requirePageSession()`). **Members list (D6):** `/admin/foro/miembros` (`app/admin/foro/miembros/`, `requirePageSession()`, so ADMIN and EDITOR): a plain list of the forum's members for moderators, newest first, 20 per page (`FORUM_MEMBERS_PAGE_SIZE`), each with display name, email, status, creation day and last sign-in; the Google id never leaves the server. The query string is `?q=` (name or email, ignoring case, `%` and `_` as plain text; `parseMemberListParams` in `src/interface/admin/forum/member-list-params.ts`), `?estado=suspendidos` and `?pagina=`. The read is `getAdminForumMembers()` (`forum-moderation-read.ts`) → `ListForumMembersUseCase` (`src/application/forum/forum-members.use-cases.ts`) over `ForumMemberDirectory`, a second port the member repository implements next to `ForumMemberRepository` (`ForumMemberPrismaRepository.list`). A suspended member has «Reactivar la cuenta» (`ReactivateButton`), which calls the same `setForumMemberSuspended(id, false)` action as the report card — same use case, audit entry and messages; that action revalidates both `/admin/foro/reportes` and `/admin/foro/miembros`. There is no suspend, delete or ban there: suspending stays on the report card. Covered by `forum-members.test.ts`, `member-list-params.test.ts`, `admin-forum-members-page.test.ts`, `admin-forum-member-controls.test.ts` and `e2e/forum-members-admin.spec.ts`. The category actions stay ADMIN only: their screens are `/admin/foro/categorias` (list with thread counts, delete), `/admin/foro/categorias/new` and `/admin/foro/categorias/<id>/edit` (all `requirePageSession("ADMIN")`), so an editor is sent back to the home. There is no reorder or archive: a new category goes last and a blank description or slug on edit keeps the current one.
- Reactions and best answer (S10e): `src/interface/forum/forum-helpful.ts` (toggle on a thread or a reply, answers `reacted` and `count`; its name must not end in `actions.ts`, or the policy-coverage test takes it for an admin module), `forum-best-answer.ts` (`setForumBestAnswer(threadId, replyId | null)`, author only) and the read `getForumReactions` in `forum-reactions-read.ts` (counts and "mine", never who). The best-answer write checks in the database transaction that the reply belongs to the thread (`reply.threadId`), is not hidden and that the thread is neither hidden nor locked (the reply is read under `FOR SHARE`, so a racing hide cannot leave a hidden answer); the foreign key alone does not check the thread, so a direct write to `ForumThread.bestReplyId` bypasses that rule.
- A locked thread is read-only for students (no replies, no edits of their own posts), and an edit re-checks author, hidden and locked state in the write itself (replies under the thread's shared row lock), so a moderator action that lands after the read wins. Editing the best answer clears the mark. Suspending a member revokes their live `ForumSession` rows in the same transaction; logout revokes the session its signed cookie names even when the guard would refuse it.
- Post text uses the Markdown subset (`src/interface/admin/markdown-subset.ts`), with fenced code blocks only when asked for (`{ codeBlocks: true }`); the news grammar the landing renders is unchanged.

## Server actions are guarded individually

The proxy (`proxy.ts`, Node runtime; named `middleware.ts` and run on the edge before the Next 16 rename) only guards `/` and `/admin/*`, matched on the raw path and on its decoded form, with a backslash read as a slash and repeated slashes collapsed (Next 16 does the same), so `/%61dmin`, `/admin%2Fevents` or `/%5Cadmin` are guarded too (`isProtectedPath` in `proxy.ts`; the matcher has an entry for every path containing `%5C` or a literal backslash, because no other entry matches those spellings, and also lists `/foro`, `/foro/:path+`, `/inscripciones/:path+`, `/invitacion/:path+` and `/api/public/events/:path+`, but only so the proxy can answer `400 Bad request` for a path with a malformed percent escape such as `/foro/eventos/%E0%A4%A` or `/inscripciones/%E0%A4%A`, which Next 16 would otherwise turn into a `500`, and, for the `/foro` and `/inscripciones` ones, move the legacy forum session cookie (see "The forum is a separate zone"); those paths get no session check), but a server action can be POSTed to any page that bundles it. Every admin server action must therefore call `requireSession()` (any signed-in user) or `requireRole("ADMIN")` (`src/interface/auth/require-session.ts`) as its first statement, must have a row in `src/tests/support/action-policy.ts` (its role and the audit entry it writes), and must have a test proving it rejects without a session and writes nothing (see `src/tests/unit/interface/admin/events/actions-auth.test.ts`, which also registers the role matrix and audit cases). `action-policy-coverage.test.ts` fails when an actions module or an action has no row, so a new action cannot ship without a decision about who may call it. Pages and the reads that feed them use `requirePageSession()` instead (it redirects rather than throws). Any new admin API route must also be added to the proxy matcher and accepted by `isProtectedPath`.

## Users, sessions, roles and audit

- **Tables** (`20261026120000_add_users_sessions_audit`): `User` (lower-cased unique email, role `ADMIN`/`EDITOR`, `active`, `lastLoginAt`), `Session` (one row per login: `kind` `user` or `break_glass`, `expiresAt`, `revokedAt`, `lastSeenAt`, short user agent, keyed hash of the client address, never the address) and `AuditLog` (append-only: time, actor id/kind `user`/`break_glass`/`system`, `action`, `entityType`, `entityId`, a short `summary`).
- **Session cookie** (`admin_session`): a signed token (HS256, 24 hours: `SESSION_DURATION_SECONDS` in `src/infrastructure/auth/session-jwt.ts`) carrying `sid`, `kind`, `uid` and a `role` hint. It only names the session; `requireSession()` loads the `Session` row on every action and page read (not revoked, not expired, user active; break-glass also needs the emergency login to be enabled) and takes the role from the user's row. `requireRole("ADMIN")` adds the role check. Cookies are `httpOnly`, `sameSite=lax`, `secure` in production; a login creates a new session and revokes the one the browser presented.
- **Who can do what**: content (events, news, FAQ, commands, board, pillars, socials, sponsors), the trash and restoring, bulk actions and reordering, forum moderation (`/admin/foro/reportes`, `/admin/foro/miembros`) and the registration overview and per-event list are for any signed-in user (`EDITOR` or `ADMIN`); site settings, deleting for good (including the unused-image cleanup), users and invitations, forum categories, exporting or deleting registrations and the audit log are `ADMIN` only; sessions: own for anyone, all for an admin. Pages hide what a role cannot use (`adminOnly` in `app/admin/_components/nav-items.ts`), but the actions enforce it (`src/tests/support/action-policy.ts`). The last active admin can be neither demoted nor deactivated (`LastAdminError`).
- **Google outage vs. refusal.** When the token endpoint is unreachable or answers 5xx, or Google's signing keys cannot be fetched (network error, timeout, non-200, unusable key set), the callback redirects to `/login?error=verification` ("No pudimos verificar su cuenta de Google. Intente de nuevo en unos minutos."), reports `failure: unavailable` and writes no `login.failure` entry. A bad or reused code, a bad signature, wrong claims or an account that is not on the list keep their own messages ("No se pudo completar el acceso…", "Esta cuenta no tiene acceso."). The operator's action is to wait and retry, and to use the emergency procedure in [DEPLOY.md](DEPLOY.md#emergency-procedure-break-glass) if it persists.
- **Invites** (`20261026160000_add_admin_invites`, table `AdminInvite`): the only way to add a user from the UI. An `ADMIN` creates one for an email and a role; the token (32 random bytes, base64url) appears once in the link `<AUTH_URL>/invitacion/<token>` and only its SHA-256 hash is stored. `/invitacion/<token>` is public, `noindex`, shows the invited email and role while the invite is pending and a neutral "no disponible" otherwise, and links to `/auth/google/start?invite=<token>`. A malformed `invite` value is refused with `/login?error=invite` before any cookie is set; a well-formed one is sealed into the OAuth flow cookie, and the callback redeems it (`RedeemAdminInviteUseCase`) instead of the normal login: the Google email must be verified, inside `ALLOWED_EMAIL_DOMAIN` when set, and equal the invited email. Redemption creates the user and marks the invite used in one transaction, so two concurrent redemptions cannot both win. Every refusal (mismatch, used, revoked, expired, unknown, email already registered) looks the same to the person (`/login?error=invite`) and writes only `login.failure` "Invitación rechazada". Invites last 7 days; creating one for an email revokes that email's older pending invite.
- **Audit entries** are written by the interface layer after each successful mutation (`event.create`, `news.trash`, `faq.purge`, `settings.update`, `user.role_change`, `invite.create`, `invite.redeem`, `invite.revoke`, `session.revoke`, `session.revoke_others`, `login.success`, `login.failure`, ...) through one `AuditRecorder` port. A failed write is logged and reported, never surfaced to the person. A `?pagina=` past the last page shows the last page. `/admin/registro` lists them newest first, 25 per page, filtered by entity type and actor.
- **Active sessions** (`/admin/sesiones`) are grouped by person (the emergency login is its own group; an ADMIN sees everyone, anyone else only their own). «Cerrar sesión» is `revokeSession(sessionId)`. «Cerrar las demás» (`revokeOtherSessions(userId)`, `src/interface/admin/sessions/actions.ts`; «Cerrar todas» on another person's group) starts with `requireSession()` and revokes that person's sessions through `RevokeOtherSessionsUseCase`, which asks the same permission as a single revoke (own sessions for anyone, someone else's for ADMIN, `ForbiddenError` otherwise) and **never revokes the caller's current session**. One `session.revoke_others` audit entry (the person's id, the count) is written only when something was closed. The emergency group has no bulk button.

## Cómo colaborar

Este panel es parte de un proyecto de la comunidad de ASO Computación y la directiva lo mantiene junto con quien quiera aportar.

- **Contenido** (eventos, fotos, FAQ, directiva, pilares, redes): se edita en el panel desplegado, sin tocar código.
- **Código**: Pull Request contra `main`. `main` está protegida, así que todo cambio entra por PR con una aprobación y la CI tiene que pasar en verde (lint, typecheck, tests, integración y build). Conviene correr lo mismo localmente antes de pedir revisión.
- **Errores e ideas**: abra un issue con las plantillas del repositorio.

La guía completa, con el flujo de ramas, las reglas de seguridad y privacidad que todo PR respeta y las buenas prácticas para la directiva, está en [CONTRIBUTING.md](../CONTRIBUTING.md). Las vulnerabilidades se reportan en privado según [SECURITY.md](../SECURITY.md).
